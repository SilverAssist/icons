# Icon Microsite Implementation Plan

## Problem Statement

There is no way to browse the 169 icons `@silverassist/icons` ships without reading source
files or the generated icon list. Issue #74 asks for a documentation microsite — a searchable
gallery plus, per icon, a live sandbox (size/color controls) and a copyable code snippet, the
way lucide.dev lets you explore its icon set. `agents-toolkit` already built the sibling of this
site (a Vite + React catalog for its skills/prompts/instructions), so this plan reuses that
stack and structure rather than inventing a new one, and adds the one piece it doesn't have: the
per-icon interactive sandbox.

## Current Architecture

- `src/icons/*.tsx` — 169 React components, one per icon, named `{Name}SVG`. Props:
  `width`, `height`, `fill` (defaults `50`, `50`, `#003073`). Verified 168/169 icons actually
  respect `fill` for recoloring; `GenericIconsAlt123.tsx` has one hardcoded fill (pre-existing,
  unrelated to this work).
- `src/icons/index.ts` — auto-generated barrel, `export { XSVG } from "./X"` per icon.
- 7 icons carry non-semantic filenames from the original SVG import (`GenericIcons70`,
  `GenericIcons79`, `GenericIcons80`, `GenericIcons81`, `GenericIcons82`, `GenericIcons83`,
  `GenericIconsAlt123`) — no human-readable name to show in a gallery card.
- No `site/` directory exists yet. Root `eslint.config.mjs` / `.prettierignore` currently cover
  the whole repo; adding `site/` means carving out an ignore the way `agents-toolkit` did.
- Reference implementation: `agents-toolkit/site/` — Vite + React 19 + React Router + Tailwind
  v4 + shadcn/radix-ui, `lucide-react` for the site's own UI icons, dark theme with monospace
  accents, modeled visually on skills.addy.ie. Deployed via `.github/workflows/deploy-site.yml`
  to GitHub Pages, triggered on push to its default branch touching `site/**`.

## Stack Context

- `react`: installed `^19.2.3`, latest `19.3.0` — patch/minor gap, nothing that changes this
  plan.
- `typescript`: installed `^6.0.3`. Latest is `7.0.2`, but this repo (like the rest of the
  group) deliberately holds at `^6.x` this cycle — not relevant to the site, which gets its own
  independent `typescript` devDependency anyway.
- No `next`, no `tailwindcss`, no `components.json` (shadcn) currently in this repo — all three
  are new, scoped entirely to `site/package.json`, exactly as they are scoped to
  `agents-toolkit/site/package.json` today (the root `icons` package.json is untouched).

## Proposed Changes

### Overview

Add a `site/` directory: a self-contained Vite + React SPA, independent `package.json`,
independent lint/format tooling, deployed to GitHub Pages. Three views: a home/landing page, an
icon gallery (search + grid), and an icon detail page with live controls, preview, and a
copyable code snippet. Content (the list of icons + display names) is generated by a script that
reads `src/icons/*.tsx` at build time — no hand-maintained icon metadata file.

**Tone**: reference documentation, not marketing. Mirror `agents-toolkit/site`'s copy register —
e.g. its hero line is "A reference for what's already built into your Claude Code, Copilot, or
Codex setup — so you reach for an existing skill instead of reinventing it," not "the best icon
library for your next project." No comparison-shopping language, no calls to action aimed at
acquiring new consumers of the package — this is for people who already have it installed.

### Technical Approach

**Directory structure** (mirrors `agents-toolkit/site/`):

```text
site/
├── package.json              # own deps: vite, react, react-router-dom, tailwindcss v4,
│                              # @tailwindcss/vite, radix-ui bits actually used, lucide-react
│                              # (site chrome only, NOT a dependency of the icons package itself)
├── vite.config.ts            # base: process.env.VITE_BASE_PATH, @/ alias to ./src
├── tsconfig.json / tsconfig.app.json / tsconfig.node.json
├── index.html
├── scripts/
│   └── generate-content.mjs  # reads ../src/icons/*.tsx, writes src/content/generated.json
├── src/
│   ├── main.tsx, App.tsx
│   ├── content/
│   │   ├── generated.json    # NOT committed (gitignored, regenerated by predev/prebuild)
│   │   ├── types.ts
│   │   └── index.ts
│   ├── components/
│   │   ├── catalog/
│   │   │   ├── icon-card.tsx        # gallery grid item
│   │   │   ├── icon-sandbox.tsx     # the new piece: controls + live preview
│   │   │   ├── code-block.tsx       # multi-line snippet w/ syntax highlight + copy button
│   │   │   └── section-heading.tsx  # reused pattern from agents-toolkit
│   │   └── ui/                # shadcn primitives actually used (button, input, slider, etc.)
│   └── pages/
│       ├── home.tsx
│       ├── icons-index.tsx    # gallery: search input + responsive grid of icon-card
│       └── icon-detail.tsx    # sandbox + snippet, one per icon
├── .gitignore                 # src/content/generated.json, dist/
```

**`scripts/generate-content.mjs`** — simpler than agents-toolkit's version (no markdown
frontmatter to parse):

1. Read every `.tsx` file in `../src/icons/`, skip `index.ts`.
2. For each file, derive: `slug` (kebab-case of the filename), `componentName` (the exported
   `{Name}SVG`), `displayName` (the filename, space-split from PascalCase — e.g.
   `AllDayDining` → "All Day Dining").
3. For the 6 non-semantic names (`GenericIcons70` and siblings), either exclude them from the
   default gallery view or tag them `unnamed: true` so the UI can filter them out of search by
   default (decision: **exclude from search results, still directly linkable by slug** — see
   Risk Assessment).
4. Write `src/content/generated.json`: an array of `{ slug, componentName, displayName }`.
5. Wire into `package.json` as `predev`/`prebuild`, same as agents-toolkit.

**`icon-sandbox.tsx`** — the new component, no equivalent in agents-toolkit/site:

- State: `size` (number, default 50), `fill` (hex color string, default `#003073`).
- Controls: a size slider or numeric input (reasonable range, e.g. 24–200px), a color input
  (native `<input type="color">` is enough — no need for a swatch picker library).
- Live preview: renders the actual icon component (dynamically imported by `componentName`
  from the generated content) with `width`/`height`/`fill` bound to the sandbox state.
- Snippet: a template string built from the current state —

  ```tsx
  import { {componentName} } from "@silverassist/icons";

  <{componentName} width={size} height={size} fill="{fill}" />
  ```

  rendered through `code-block.tsx` (extend agents-toolkit's `CodeBlock` — that one is
  single-line; this needs multi-line with syntax highlighting, so use
  `react-syntax-highlighter`, already a proven dependency in the reference site) with the same
  copy-to-clipboard button pattern.

**Root repo changes** (per your note: `site/` gets its own tooling, same carve-out as
agents-toolkit):

- `eslint.config.mjs`: add `"site/**"` to the existing `ignores` array (alongside
  `node_modules/`, `temp-svgs/`, etc.).
- `.prettierignore`: add a `site` entry with the same comment agents-toolkit uses ("self-contained
  Vite app with its own tooling — the root pipeline doesn't reach into it").
- Root `package.json` `check` script: unchanged, does not reach into `site/`.
- `site/package.json` gets its own `lint` (`oxlint`, matching agents-toolkit — zero-config, fast,
  no need to duplicate the root's typescript-eslint setup for a throwaway SPA), `format` /
  `format:check` (Prettier defaults), `typecheck` (`tsc -b`), `build`.

### API Changes

None to the published `@silverassist/icons` package — the site only imports and renders
existing exports, it does not modify `src/icons/`.

### Caching Impact (Next.js)

Not applicable — `site/` is a static Vite SPA with no Next.js involved and no data fetching
beyond reading its own build-time-generated JSON.

## Risk Assessment

| Risk                                                                              | Probability                         | Impact                                                   | Mitigation                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------- | ----------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 6 non-semantic icon names look broken in a searchable gallery                     | High (already true today)           | Low                                                      | Exclude them from default search/grid via a generated `unnamed` flag; keep them reachable by direct slug so nothing is silently dropped from the data set. Revisit real renames as a separate, unrelated fix.  |
| `fill`-based recolor assumption breaks if a future icon hardcodes internal colors | Low today (1/169)                   | Medium (sandbox color control would silently do nothing) | Generation script can flag icons whose SVG source contains a hardcoded hex outside the `fill` prop, surfaced as a subtle "custom colors" badge instead of failing silently.                                    |
| GitHub Pages requires one-time repo setting                                       | Certain, one-time                   | Blocks deploy until done                                 | Settings → Pages → Build and deployment → Source → "GitHub Actions" — same step agents-toolkit's README documents. Call out explicitly before merging the deploy workflow.                                     |
| `site/` accidentally pulled into root CI (`npm ci`, `npm run check`)              | Low if ignores are copied correctly | Medium (root install breaks importing unrelated deps)    | Verify root `package.json`'s `check`/`lint`/`format:check` scripts never `cd site` or glob into it; confirmed pattern from agents-toolkit already excludes it entirely (own `package-lock.json`, own CI step). |

## Phase Breakdown

### Phase 1: Site scaffold

**Objective**: A running Vite + React app with routing and the dark/mono theme, no icon content
yet — prove the shell before wiring real data.

- [ ] `site/` directory: `package.json`, `vite.config.ts`, `tsconfig*.json`, `index.html`,
      copied/adapted from `agents-toolkit/site`
- [ ] Tailwind v4 + shadcn primitives actually needed (button, input, slider or equivalent) —
      not the full agents-toolkit component set, only what the gallery/sandbox use
- [ ] `App.tsx` with React Router: `/`, `/icons`, `/icons/:slug`
- [ ] Root `eslint.config.mjs` gets `"site/**"` added to `ignores`; root `.prettierignore` gets
      the `site` entry
- [ ] `site/package.json` has its own `lint` (oxlint), `format`, `format:check`, `typecheck`,
      `build`, `dev` scripts, fully independent of root

**Validation**: `cd site && npm install && npm run dev` serves an empty shell with working
routes; `cd .. && npm run check` at the repo root still passes and never touches `site/`.

### Phase 2: Content generation + gallery

**Objective**: Every icon is browsable and searchable.

- [ ] `site/scripts/generate-content.mjs` reads `../src/icons/*.tsx`, writes
      `src/content/generated.json` with `{ slug, componentName, displayName, unnamed }`
- [ ] Wire `predev`/`prebuild` to run it automatically, gitignore the generated file
- [ ] `icons-index.tsx`: search input (client-side filter on `displayName`) + responsive grid of
      `icon-card.tsx`, each rendering the real icon at a small fixed size
- [ ] `home.tsx`: landing page, reference tone, links into `/icons`

**Validation**: `npm run build` produces a working static site with all 169 icons rendered in the
grid (163 in default search results, 6 unnamed ones excluded from search but reachable
directly); typing in the search box filters live.

### Phase 3: Icon sandbox + snippet

**Objective**: The piece the issue actually asked for — per-icon live customization and copyable
code.

- [ ] `icon-detail.tsx` route (`/icons/:slug`), 404/redirect to `/icons` on an unknown slug
      (same pattern as agents-toolkit's `skill-detail.tsx`)
- [ ] `icon-sandbox.tsx`: size control, color control, live preview bound to state
- [ ] `code-block.tsx` (multi-line variant): renders the current import + JSX snippet via
      `react-syntax-highlighter`, copy-to-clipboard button
- [ ] Snippet updates in real time as sandbox controls change

**Validation**: Manually verify on 5–10 icons spanning both "Large" and "Small" original sizes
that the preview updates live and the copied snippet, pasted into a scratch file, produces
working JSX.

### Phase 4: Deploy

**Objective**: The site is live and stays current automatically.

- [ ] `.github/workflows/deploy-site.yml`, adapted from agents-toolkit's (trigger on push to
      `master` — this repo's default branch, not `main` — touching `site/**` or `src/icons/**`;
      `VITE_BASE_PATH=/icons/`; copy `index.html` → `404.html`; `.nojekyll`)
- [ ] One-time manual step (documented in this plan, performed by a human with repo admin):
      Settings → Pages → Source → "GitHub Actions"
- [ ] `site/README.md` documents the content pipeline, mirroring agents-toolkit's site README
      structure ("How content gets in", commands, deployment)

**Validation**: A push touching `site/**` triggers the workflow; the deployed URL
(`https://silverassist.github.io/icons/`) serves the gallery and a detail page resolves on a
hard refresh (not just client-side navigation).

## Testing Strategy

### Unit Tests

Not planned for `site/` itself — it's a static content-driven SPA with no business logic beyond
the generation script and the sandbox's derived-state rendering, matching agents-toolkit's site
(which also ships no unit tests). If the generation script's slug/display-name derivation grows
edge cases, a small script-level test (`node --test` or a one-off assertion script) is cheap to
add then.

### Integration Tests

None planned initially — no Playwright/e2e harness for `site/`, consistent with
agents-toolkit/site.

### Manual Testing

- Search filters correctly across the full 169-icon set, including partial/case-insensitive
  matches
- Every icon detail page loads without a console error (spot-check a sample, not all 169)
- Copied snippet is syntactically valid and renders when pasted into a real component
- Direct URL to `/icons/:slug` for one of the 6 unnamed icons still resolves despite being
  excluded from search
- Mobile viewport: gallery grid and sandbox controls remain usable at ~375px width

## Rollback Plan

`site/` is fully additive — no changes to `src/icons/`, no changes to the published package's
`exports`, `main`, or `types`. Reverting is deleting the `site/` directory, the
`deploy-site.yml` workflow, and the two ignore-file entries; nothing published to npm is
affected either way.

## Dependencies

- External: `vite`, `@vitejs/plugin-react`, `react-router-dom`, `tailwindcss` v4 +
  `@tailwindcss/vite`, whichever `radix-ui`/shadcn primitives the gallery/sandbox actually use,
  `lucide-react` (site chrome icons only), `react-syntax-highlighter`, `oxlint` — all scoped to
  `site/package.json`, none added to the root package.
- Internal: none blocking. `next-testing-toolkit`'s `ESLINT_IGNORE_PATTERNS` already covers
  fixture/build globs at the root and needs no change for this work.
- Infrastructure: GitHub Pages must be enabled for this repo (Settings → Pages → Source →
  GitHub Actions) before the deploy workflow can publish — confirmed via the API
  (`GET repos/SilverAssist/icons/pages` → 404) that this was **not enabled** when this plan
  was written. Enabled during Phase 4 implementation via
  `POST repos/SilverAssist/icons/pages` with `build_type: workflow`.
- Team coordination: none — this is additive tooling in a repo with no other active work in
  flight on `site/`.
